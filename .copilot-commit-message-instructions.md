# Commit message generation

Generate the commit message from the actual staged diff. Do not reuse a recent
commit message or infer the change from only one comment or documentation edit.

The subject must identify the most important concrete behavior, feature, fix, or
configuration changed. Prefer a result-oriented imperative verb such as `Add`,
`Fix`, `Improve`, `Tune`, `Optimize`, `Remove`, or `Document`.

Never use these vague fallbacks:

- `Refactor code structure for improved readability`
- `Refactor code for readability and maintainability`
- `Update code`
- `Miscellaneous changes`
- `WIP`

Use `Refactor` only when the diff is genuinely structural and has no user-visible
behavior change. Even then, name the specific system and purpose, for example
`Refactor jump trajectory calculation into shared helpers`.

Include the affected gameplay or project system in the subject when it is useful:
jump aiming, camera focus, landing preview, airborne animation, cursor capture,
WebGL build, documentation, project settings, scenes, or prefabs.

For a mixed diff, summarize the primary functional outcome rather than listing
internal file operations. If several independent behaviors changed together,
mention the second important behavior in a concise subject or body.

Keep the subject under 72 characters. Add a body only when it clarifies why the
change was needed or what was tested. Do not explain obvious file additions,
renames, comments, or formatting as the main purpose of a commit.

Examples:

```text
Add vertical aiming to spider jumps
```

```text
Keep jump landing marker centered in camera view
```

```text
Tune cursor capture for Unity play mode
```

```text
Document WebGL hosting and PSX visual constraints
```
